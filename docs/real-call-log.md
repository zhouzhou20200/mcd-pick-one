> ✅ 绝大多数调用为**只读**工具。
> ⚠️ 全部四批中共有 **2 次写操作**，均经用户明确同意后执行：`auto-bind-coupons`（领券，批次三）、`delivery-create-address`（建配送地址，批次四）。

## 4. 关键发现（20 条）

### 4.1 ⚠️ 菜单按时段切换，跨时段的设计不能复用

调用 8 时服务器时间为 **10:03**，落在门店档期的「早餐 06:14–10:15」区间内。因此 `query-meals` 返回的是**早餐菜单**：麦满分系列、厚松饼堡系列、麦咖啡、炒双蛋堡……

**整个返回里没有麦辣鸡腿堡，也没有巨无霸。**

原 README 用"麦辣鸡腿堡约 23 元、巨无霸约 25.5 元"来论证"25 元吃饱无解"——该论证**只在正餐时段成立**。项目必须把"当前时段"作为取菜单的前置条件，否则给出的推荐是错的。

> ⚠️ **本条在批次二中被进一步修正**：把"档期"当作取菜单的前置条件**本身并不可靠**——档期与实际可售菜单存在不同步窗口。详见 **4.5**。

### 4.2 ⚠️ "券驱动"在本例中失效，必须有无券路径

`query-store-coupons` 返回**空数组**、`query-my-coupons` 显示**券包为空**。也就是说，本次真实环境下**一张可用券都没有**。

如果项目把"把价格压进预算"完全押在券上，此刻它会直接失败。**真实结论：券是加速器不是地基**，必须有"无券时按菜单价精算单品组合"的降级路径。

### 4.3 ✅ 无券时「25 元吃饱」在早餐时段**有解**

真实菜单价组合：

| 组合 | 主食 | 配餐 | 合计 |
|------|------|------|:--:|
| 最低价组合 | 吉士蛋麦满分 10.5 元 | 脆薯饼 9 元 | **19.50 元** |
| 次低 | 火腿扒麦满分 11.5 元 | 脆薯饼 9 元 | 20.50 元 |
| 第三 | 大脆鸡扒麦满分 12.5 元 | 脆薯饼 9 元 | 21.50 元 |

三者都**满足「主食 + 配餐」结构且 ≤ 25 元**，且已由 `calculate-price` 实测验证（见 3.1）。

→ 修正后的表述应为：**"25 元吃饱在正餐时段几乎必须靠券，在早餐时段可直接靠单品组合达成。"**

### 4.4 📌 两条有价值的实现细节

1. **无券无活动时，`calculate-price` 总价 = 各单品菜单价之和**（1050 + 900 = 1950 ✓）。
   说明菜单价可用于**预筛**，但一旦存在券或活动就**必须**走 `calculate-price`——两者的结果会分叉。
2. **`takeWayList` 只会返回「堂食 / 外带」**，这是 `orderType=1`（到店）内部的取餐方式。
   它与"外送"（`orderType=2`）是两个不同层级的概念——需求里说的"外带"正好落在这里，代码中不能与外送混用。

### 4.5 ⚠️ 门店「档期」≠ 实际可售菜单（**修正了 4.1 的实现方式**）

批次二 10:28 抓到的门店档期，与批次一 10:03 对比：

| 抓取时刻 | `1980320` 今日档期（`reservationOptionText`） |
|----------|---------------------------------------------|
| 10:03 | `早餐(06:14至10:15)，午餐(10:44至14:15)，下午茶…` |
| **10:28** | `午餐(10:44至14:15)，下午茶…` —— **早餐档已从列表中消失** |

但**同一时刻**（10:28）：

- `query-meals` 返回的**仍然是早餐菜单**（麦满分系列、厚松饼堡、麦咖啡、炒双蛋堡）；
- `calculate-price` 对早餐品（`5888 + 4825`）核价**成功**，返回 1950 分。

**结论：档期是「可预约时段」，不是「当前可售菜单」，两者存在不同步窗口（本例 ≥ 13 分钟）。**

→ 4.1 里"**先把档期作为取菜单的前置**"这条实现方式**不足以保证正确**。
→ 正确做法：**以 `query-meals` 的实际返回为准**（那才是下单时真正可选的商品）；档期只用于 ① 判断能否预约 ② 提示"当前正处于档期切换窗口"。

### 4.6 ✅ 官方数据自带「主食 / 小食 / 饮料」分类

`query-meal-detail` 返回的 `rounds[].name` 直接就是分类名（见 3.4）：

```
round 1 → "吉士蛋麦满分"          ← 主食
round 2 → "选择早餐套餐小食"      ← 配餐
round 3 → "选择早餐套餐饮料"      ← 饮料
```

**「主食 + 配餐」的结构判定不必自建词表。** `pick_one.py` 现在的 `MAIN_ROLES` / `SIDE_ROLES` 是手写分类，会随新品（如「德式图林根香肠」）失效；而 round 名称由官方维护，更稳且**能直接区分饮料**——恰好解决了 4.4 提过的"配餐含不含饮料"这个歧义。

> 本次**未改代码**（保留 `pick_one.py` 纯离线、零依赖的特性），但已作为取值建议写入 [`src/SKILL.md`](../src/SKILL.md)。

### 4.7 💰 套餐不一定比单点便宜（"算出来"的价值实证）

| 方案 | 构成 | 价格 |
|------|------|:--:|
| 套餐 `9900003477` | 吉士蛋麦满分 + 脆薯饼 + 鲜萃冰咖 | **30 元** |
| 单点组合 | 吉士蛋麦满分 `5888`（10.5）+ 脆薯饼 `4825`（9） | **19.50 元** |

差额 **10.50 元**，正好是那杯饮料。对"只要吃饱、不要饮料"的用户，**单点组合比套餐省 35%**。

→ 这条正面支撑项目核心主张：**菜单价 / 套餐价本身判断不出"哪种更省"，必须按用户的结构偏好重算。**

### 4.8 ⚠️ 「优惠」不止券一类，共三类

| 类别 | 证据 | 说明 |
|------|------|------|
| ① 券 | `available-coupons` 可领 8 条 / `query-my-coupons` 券包 0 / `query-store-coupons` 本店 0 | 需领取后才有券码 |
| ② **随单购卡** | `discountType` = `随单购早餐卡优惠`、`withOrder.cardId` | 例：麦咖啡 25 元 → **9.9 元** |
| ③ **活动价** | `campaign-calendar` | 例：麦金卡套餐、厚松饼堡早餐卡 6 折 |

→ 原设计的"**券驱动**"应升格为「**优惠驱动**」，券只是三类之一。

### 4.9 📌 未领取的券无法代入核价 —— 「券前置」的实证理由

`available-coupons` 中有**「免费脆薯饼」**。若该券生效，今天这单可从 19.50 元降到 **10.50 元**。

但 `calculate-price` 的券参数需要 `couponId` / `couponCode`，**未领取的券拿不到券码，无法试算**。

→ 结论：券必须是**决策输入**而非展示信息——流程里要设「**领券前置**」：发现可领券 → 征询用户 → 领取 → **重算** → 再给答案。
→ 把券放在答案末尾当提示，等于**在最该省钱的时候先做了决定**。

### 4.10 ⚠️ 「领到了」≠「能用」——券的可用性是三层过滤（批次三）

**批次三（2026-10-11）** 征得用户同意后，首次调用写操作 `auto-bind-coupons` 领取麦麦省全部 6 张券。
接口返回"总计 6 张 / 成功 6 张 / 失败 0 张"，但随后三处查证全部指向相反结论：

| 层 | 接口 | 返回 |
|:--|:--|:--|
| 可领 | `available-coupons` | 6 张，**全部显示「已领取」** |
| 券包 | `query-my-coupons` | **共 5 张**（标题为"可用优惠券列表"）——「免费脆薯饼」**不出现** |
| **本店** | `query-store-coupons` | **空数组** —— 已有 5 张券，门店 `1980320` + 到店自取渠道**一张都用不上** |
| 核价 | `calculate-price`（带该券 `couponId` / `couponCode`） | **`success=false` / `code=600012` / `当前优惠券不可用！`** |

`query-my-coupons` 返回的 5 张券本身也带严格时段窗口，例如某张早餐券的有效期写的是
**`2026-10-11 05:00-10:29 周日 05:00-10:29`**（当日 10:29 即失效）。

→ **修正 4.9**：4.9 说"券前置、领了再算"是对的，但**不完整**。领到手只是入场券，
还要过**门店 + 渠道**这一关。`available-coupons` 的"已领取"与 `query-my-coupons` 的"在包里"
**都不能作为本单可用性的判据**，唯一判据是 `query-store-coupons`。

→ **同时修正 4.9 里的数字**：该券"若生效可降至 10.50 元"只是**理论值**，
批次三实测**未能达成**（券在本店渠道不可用）。因此最终答案仍是 **19.50 元**，
不得据推算值对外宣称 10.50 元。

### 4.11 ⚠️ 带券核价会「整体失败」，必须做降级而不是期待它回退原价

批次三中，把券代入 `calculate-price` 得到的是**整个请求失败**（`code 600012`），
而**不是**"券不可用、按原价 1950 分正常返回"。

→ 实现层面必须：**带券试算包一层降级，任何一张券导致失败就立刻退回无券路径。**
若按"带券核价总会成功"来写，整个决策引擎在这种门店下会**直接崩掉**——
连 19.50 元的基础答案都产不出来。这是"**必须有降级路径**"最硬的一条实证。

### 4.12 📌 顺手提示门槛①的真实拦截案例

批次三（10-11，**周日**）当日活动第一条是「**超值 9.9 元早餐两件套**」（10-08 ~ 10-21），
但文案明确限定「**周一至周五**早餐堡轮流上早班」。

→ 该活动**当日不适用**，在 `rank_tips.py` 的**第一层门槛（"现在就能做"）被挡下**，不进入提示候选。
这正是门槛①存在的意义：少了这一层，"9.9 元"会被当成福利推给用户，用户到店才发现用不了。

### 4.13 📌 「档期 ≠ 菜单」在批次三再次复现（确认非偶发）

批次三 10:20 取数：门店当日 `reservationTimeOptions` **只有午餐（10:44 起），根本没有早餐档**；
但 `query-meals` 仍返回**完整早餐菜单**（8 个分类 / 41 个单品），`calculate-price` 照常核价成功。

→ 与 4.5（批次二 10:28 档期已切午市、菜单仍返早餐）**现象一致**。可确认这是**稳定行为**，
而非某个时间点的巧合。**实现判据只能是 `query-meals` 的返回，不能是档期。**

### 4.14 ✅ 批次三的独立复算，再次得到同一答案

批次三对同一组合独立核价：`吉士蛋麦满分 + 脆薯饼` = **1950 分 = 19.50 元**，`discount=0`，
`takeWayList` 返回 `eat-in`（堂食）/ `locker-in`（外带）。

→ 与批次一（10-10）结果**完全一致**。两次相隔一天的独立联调给出同一最优解，
说明该结论不依赖单次取数的偶然性。

### 4.18 💰 外送固定比自取贵 7.90 元，25 元硬预算在外送场景不成立（批次四）

`calculate-price`（`orderType=2`）返回完整费用结构：

| 项 | 分 | 元 |
|:--|:--|:--|
| 商品（汉堡包 15 + 脆薯饼 9.5） | 2450 | 24.50 |
| 配送费（无减免） | 600 | **6.00** |
| 打包服务费 | 190 | **1.90** |
| **实付** | **3240** | **32.40** |

→ 外送价**已含**附加费，所以「外送 = 自取价 + 配送费」这个直觉算法是**错的**——它会重复计费。
→ 该门店外送菜单里最省的「主食 + 配餐」组合就是这一档，**最低也要 32.40 元**（超预算 7.40）。
这验证了 `src/pick_one.py` 的 `over_budget` 降级分支是**真实必需**，不是兜底摆设。

> 📌 **打包费按商品类型计**：只点饮品的那次核价（`507411` + 券）**未产生打包费字段**（=0）。
> 所以任何「写死一个固定费用」的做法在边界场景都是错的——费用只能来自核价。

### 4.19 ✅ 券在外送渠道核价成功 —— 修正 4.10 / 4.11 的推论边界（批次四）

批次三出现过「领券后带券核价整体失败」`600012`。批次四证明那**不是券机制的问题，而是那家门店不可用**：

| 项 | 值 |
|:--|:--|
| 券 | 9.9 元中杯冰美式（适用 `507411`） |
| 原价 | 1900 分 = 19.00 元 |
| 券后 | **990 分 = 9.90 元** |
| `discount` | **910 分 = 9.10 元** |
| 总计 | 1590 分 = 15.90 元（含配送 600，**无打包费**） |

→ **正确姿势是「先试算，失败再降级」**，不是「预判不可用就不试」。
→ **券的价值随渠道变化**：同一张券，到店标价 11.90（省 2.00），外送原价 19.00（**省 9.10**）——
相差 4.5 倍，因为外送标价本就更高。**试算必须在目标渠道下做。**

## 7. 复现方式

1. 按 [`mcp-config.example.json`](../mcp-config.example.json) 配置并启用 `mcd-mcp` 连接器（需自备 Token）；
2. 在 WorkBuddy 中依次提出以下请求，即可复现上表调用：

**批次一（链路 + 核价）：**

```
今天天津站附近有什么麦当劳？
麦当劳天津站后广场餐厅今天有什么可以点的？
这家店我现在有什么券可以用？
帮我算一下：吉士蛋麦满分 1 份 + 脆薯饼 1 份，到店自取多少钱？
```

**批次二（券 / 活动 / 菜单时段边界）：**

```
麦当劳天津站后广场餐厅这个月有什么活动？
我现在有什么券可以领？卡包里有什么券？
吉士蛋麦满分套餐具体包含哪些东西？
```

**批次三（券前置 → 领券 → 复算）：**

```
我有哪些券可以领？本店能用哪张？
（经确认后）帮我领一下这些券
（领券后）再用脆薯饼券算一次刚才那单，多少钱？
```

**批次四（外送链路 + 渠道差异）：**

```
天津工业大学的麦当劳，1 点左右的饭外送，有什么推荐的？
（此时会暴露"账号内无配送地址"这条硬阻断）
（经确认并提供收货信息后）帮我建一下配送地址
（建址后）现在有哪些店能送到？外送菜单有什么？
帮我算一下：汉堡包 1 份 + 脆薯饼 1 份，外送到这个地址多少钱？
用 9.9 元冰美式券算一下麦咖啡冰美式中杯，外送多少钱？
```

3. 用同批数据离线复现决策结果：

```bash
python src/pick_one.py --input src/demo.real.json                          # 到店自取（批次一 / 三）
python src/pick_one.py --input src/demo.delivery.json --channel delivery   # 外送（批次四）
```

> ℹ️ 复现结果会随**实际时间**变化——菜单随时段切换、券随账号与门店变化。
> 本文件记录的是 **2026-10-10 的实际快照**，不代表当前状态。
